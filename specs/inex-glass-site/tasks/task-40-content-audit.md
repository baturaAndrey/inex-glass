## Technical Details

### 1. Реестр мета (`meta-registry.ts`)

- Парсит таблицы `docs/inex/17-meta.md`: строки, начинающиеся с `| /`. Столбцы: URL | H1 | Title | Description (+ «Главный запрос»). **Если в строке два description (в ячейке есть « | » с продолжением — встречается у `/obrabotka-stekla/facet/`, `/kak-zakazat/oplata/`, `/proektirovanie/`) — берётся первый**, расхождение записывается в отчёт SEO как «второй description в 17-meta проигнорирован, подтвердить у заказчика».
- Экранированный `\|` в Title (бренд-разделитель «\| Inex Glass») → `|`.
- Раскрытие шаблонов для `/zakalennoe-steklo/{N}-mm/`: N ∈ {4,5,6,8,10,12,15,19}. `{цена}` — число ₽/м² из глобала `prices` (формат с неразрывным пробелом: `1 400`), только если `priceState = 'price'` (цена есть и не старше порога 45 дней; 15/19 — всегда «под заказ»); тогда ожидается вариант title «… — от {цена} ₽/м² | Inex Glass», иначе вариант «… — под заказ | Inex Glass» (в 17-meta есть строка «(без цены)»). `{вес}` = N × 2,5 кг/м² (формат: десятичная запятая, без хвостовых нулей: 10 → «25», 5 → «12,5», 15 → «37,5», 19 → «47,5»). Значения цен читаются из БД (Local API) либо из API/HTML сайта; в офлайн-режиме берутся константы сидов: 4→700, 5→750, 6→800, 8→1300, 10→1400, 12→2000.
- Сравнение строк: нормализация — NBSP→пробел, схлопывание пробелов, trim, «ё» НЕ приводить к «е» (в 17-meta «Закалённое» с «ё» — отличие — ошибка), типографские кавычки/тире сравнивать как есть.

### 2. `scripts/audit/content.ts` — правила контента (ТЗ §11)

Два режима: `--db` (Local API по всем документам: тексты Lexical, блоки `layout[]`, SEO-поля, FAQ, глобалы `conditions`, `snippets`, `navigation`, `contacts`) и `--rendered` (по умолчанию: берёт URL из `scripts/audit/urls.ts` и проверяет текст отрендеренного HTML `main` + `title` + `meta description` по `BASE_URL`; удаляет `script/style/noscript`). Для БД нужен Payload (`src/seed/context.ts`), для rendered — только HTTP.

Проверки (каждое нарушение: `severity`, URL/документ, поле, фрагмент ±40 символов):

| Правило | Что ищем | Severity |
|---|---|---|
| Стоп-слова из `site-settings.stopWords` | названия заводов-партнёров (список заказчика) | error |
| `Heat Soak`, `HST`, `ГОСТ 24866` (стеклопакеты), `стеклопакет` | регистронезависимо, учитывать словоформы (`стеклопакет\w*`) | error |
| «собственное производство», «закаливаем сами», «наше производство» | | error |
| «монтаж под ключ» | допустимо только в «мосте» на inex.su (блок/ссылка «Двери, лестницы и другие конструкции Inex — на inex.su», блок `whoDoesWhat.strip`/`inexSuBridge`); контекст определять наличием ссылки на `inex.su` в том же абзаце | error |
| Спецстёкла: `бронированн\w*`, `смарт[- ]?стекл\w*`, `антиблик\w*`, `шпион\w*`, `армированн\w*`, `солнцезащитн\w*` | | error |
| Обещания, которых нет: «срочн\w+ изготовлен», «срочное производство», приём физических шаблонов, «закалка вашего стекла», «обычное (незакалённое) стекло» в смысле продажи | поиск по шаблонам; допускаются отрицательные формулировки («срочного изготовления нет») — проверять вручную, поэтому severity `warn` + выводить контекст | warn |
| Формулировка опыта | любое вхождение «21 год/лет» рядом с «проект» или «1500»: должно быть **точно** «За 21 год специалисты Inex выполнили более 1500 проектов» (число берётся из `site-settings`). Иные варианты («1500+ проектов за 21 год», «21 год, 1500+ проектов») — нарушение | error для body; **warn** для строк из `17-meta.md` (description `/obekty/` и `/o-kompanii/` используют вариант «1500+ проектов за 21 год» / «21 год, 1500+ проектов» — зафиксировать как противоречие 17-meta и ТЗ §11 → вопрос заказчику/в открытые вопросы) |
| Нераскрытые метки | `\{[^{}\s][^{}]*\}` в тексте и мета (`{цена}`, `{N}`, `{акция_текст}`…) | error |
| Цена без даты/оговорки | на страницах с цифрой «₽/м²»: рядом (в том же блоке) должна быть подпись «Ориентировочная цена на ДД.ММ.ГГГГ. Точная стоимость — в КП; цена в договоре фиксируется» | error |
| Цены вне справочника | числа с «₽» в тексте статей/страниц, не совпадающие со значениями `prices` | warn |
| Эмодзи | любые символы Unicode Emoji/Extended_Pictographic (кроме `№ ₽ × − ± ≈ ≤ ≥ → ·`) | error |
| Монтаж | утверждения «выполняем монтаж», «установим» (монтаж не выполняется); допустимо «Монтаж — ваша бригада» | warn |
| Лишнее | фразы «Хит», «Новинка», упоминания личного кабинета/корзины | warn |

- **Allowlist** `scripts/audit/allowlist.json`: массив `{ "match": "М1", "url": "/blog/markirovka-zakalennogo-stekla/", "reason": "М1 — марка листового стекла (ГОСТ), не название завода" }`. «М1» не встроенное стоп-слово (task-11), но заказчик может внести его в `site-settings.stopWords` как завод. Тогда оно конфликтует с легитимной статьёй «Марки и маркировка стекла» (title в 17-meta содержит «Стекло М1»), поэтому allowlist обязателен, иначе аудит даст ложную ошибку. В тестах сида task-31 то же исключение задано через `ignoreRules: ['partner-factory']`. Каждое исключение — с причиной; скрипт печатает, какие исключения сработали.

### 3. `scripts/audit/seo.ts` — проверки по каждому URL

Вход: `BASE_URL` (по умолчанию `http://localhost:3000`) + `scripts/audit/urls.ts` (все URL из `sitemap.xml` + известные noindex-страницы + ожидаемый список из 17-meta). Загрузка HTML через `fetch` (редиректы не следовать вручную для проверки кодов). Парсинг `cheerio`.

1. **Доступность и URL:** 200; без редиректа; путь в нижнем регистре и со слешем; для каждого URL из выборки (≥ 10) проверить редиректы: версия **без слеша** → 301/308 на канонический (Next при `trailingSlash: true` использует 308 — допустимо и 301, и 308; зафиксировать в отчёте, что Яндекс/Google трактуют 308 как постоянный); **верхний регистр** (`/Zakalennoe-Steklo/`) → 301 на нижний (proxy.ts, task-01).
2. **Покрытие реестра:** каждый URL из `17-meta` (после раскрытия) отвечает 200, и наоборот — каждый URL из sitemap есть в реестре 17-meta или в списке известных дополнительных (`/obekty/{slug}/`, `/blog/page/N/`, `/obekty/page/N/`, служебные). Лишние — warn.
3. **H1:** ровно один `<h1>` и совпадает с H1 из 17-meta (после нормализации). Для `/` — «Закалённое стекло и стеклянные конструкции для ваших проектов».
4. **Title/Description:** `<title>` и `<meta name="description">` совпадают с реестром (первый description). Длины: title ≤ 65 знаков (warn при превышении), description 120–160 (warn). Дубликаты title/description между разными URL — error.
5. **Robots:** `noindex, follow` (в `<meta name="robots">`) **обязателен** для: `/zakalennoe-steklo/5-mm/`, `/15-mm/`, `/19-mm/`, `/politika-konfidencialnosti/`, `/soglasie-na-obrabotku-personalnyh-dannyh/`, `/poisk/`, `/zakaz/<token>/`, фильтров `/obekty/?product=…` (canonical → `/obekty/`), `/o-kompanii/sotrudniki/` при пустой коллекции `team`; **отсутствует** у всех остальных страниц из sitemap. Пагинация `/obekty/page/2/`, `/blog/page/2/`: index, canonical на себя, title содержит «страница 2».
6. **Canonical:** абсолютный (`SITE_URL` + путь со слешем), без query; у страниц с query (`?utm_*`, `?filtr`) — на чистый URL.
7. **Хлебные крошки:** на всех страницах, кроме `/`, есть видимый `nav[aria-label="Хлебные крошки"]` (или реальный селектор из task-13) и JSON-LD `BreadcrumbList`; число элементов = глубина URL + 1 (главная); последний элемент — название страницы; `item` — абсолютные URL, позиции 1..n.
8. **JSON-LD:** каждый `<script type="application/ld+json">` — валидный JSON; ожидания:
   - Главная: `Organization` (name «Inex Glass», url, logo) и `LocalBusiness` для двух офисов (Челябинск, Екатеринбург: адрес, телефон, часы; допускается на `/kontakty/`);
   - Карточки толщин 4/6/8/10/12: `Product` + `AggregateOffer` (`lowPrice` = цена из `prices`, `priceCurrency: "RUB"`) **только пока `priceState = 'price'`**; на 5/15/19 мм и при просроченной цене — `Product`/`AggregateOffer` **отсутствуют** (не должно быть `offers`);
   - Страницы с FAQ — `FAQPage` (`mainEntity` непустой, число вопросов = числу вопросов на странице);
   - Статьи — `Article` (`headline`, `datePublished`, `dateModified`, `author`, `image` если есть);
   - Нет JSON-LD с пустыми значениями, `undefined`, `NaN`, незаполненными метками `{…}`.
   Дополнительно (рекомендация человеку): прогнать ключевые шаблоны через https://validator.schema.org/ и валидатор микроразметки Яндекса — вручную, результат занести в отчёт.
9. **Open Graph/Twitter:** `og:title`, `og:description`, `og:url`, `og:type`, `og:image` (абсолютный URL, 200); `<html lang="ru">`.
10. **Изображения:** у всех `<img>` непустой `alt` (декоративные — `alt=""` допустимы только с `role="presentation"`/`aria-hidden`); нет `<img>` без `width/height` или aspect-ratio (прокси CLS).
11. **Ссылки:** собрать внутренние `<a href>` со всех страниц, дедуплицировать, проверить `HEAD`/`GET`: 200 (или 301/308 → 200 без цепочек > 1); внешние — только `inex.su`, мессенджеры, Яндекс (без проверки сети); ссылки на `/admin` — `<a>`; нет `http://`-ссылок на собственный домен; нет ссылок на несуществующие `/obekty/<slug>/` (черновики). Битые ссылки — error.
12. **Структура:** ровно один `<main id="main-content">`; нет `noindex` на страницах из sitemap; нет дублей H1/title; страница не содержит `lorem`/`TODO`/`заглушка` (кроме `.ig-ph` вспомогательных подписей, список исключений в allowlist).
13. **Скорость ответа (прокси):** TTFB HTML < 600 мс на локальном `next start` для ISR-страниц (warn при превышении).

Вывод: `docs/reports/seo-audit.md` — сводка по severity, таблица «URL × проверки» (✓/✗), список ошибок с фрагментами, список расхождений с 17-meta (diff «ожидалось / фактически»), список warn. Код выхода 1 при `error`.

### 4. `scripts/audit/wordkeeper.ts` — частотность и покрытие запросов

**Цель** (из плана): проверить после переноса, что главные запросы из 17-meta присутствуют в H1 и title и что их частотность (Wordstat через Wordkeeper) не расходится с зафиксированной в 17-meta; **автоматических правок текстов нет**, только отчёт `docs/reports/seo-frequency.md`.

**Режимы:**
1. **Офлайн (обязателен, работает всегда):** берёт из реестра столбец «Главный запрос (РФ / 3 округа)» (напр. «закаленное стекло 1374/416», «стекло триплекс 1131/391») — запрос и зафиксированные частотности (замер Wordkeeper от 15.10.2026). Для каждого URL проверяет **покрытие запроса** в H1 и в title: нормализация («ё»→«е», lowercase), лемматизация упрощённо — сравнение по основам слов (обрезка окончаний: слово ≥ 5 букв сравнивается по первым `len-2` знакам, короткие — целиком; стоп-слова-предлоги игнорируются); результат `H1: полное/частичное/нет`, `Title: …`, список отсутствующих слов запроса. Строки с «—» (нет запроса) пропускаются.
2. **Онлайн (если API доступен):** запрос частотности для каждого главного запроса → сравнение «зафиксировано 15.10» vs «сейчас» (дельта, %), отметка падения > 30%.

**Wordkeeper API — неопределённость (обязательно прочитай):** публичной документации API у сервиса word-keeper.ru найти не удалось (проверено 20.10.2026: сайт перечисляет «API доступ» как опцию тарифов, но не публикует base URL, схему авторизации и эндпоинты; по данным агрегатора toolfox.ru API входит только в старший тариф «Агентство»). Поэтому:
   - Шаг 0 (агентом): проверить `WORDKEEPER_API_KEY` (длина, формат), поискать документацию через Exa (`site:word-keeper.ru api`), в личном кабинете (недоступен агенту); если документация найдена — реализовать клиент в `scripts/audit/lib/wordkeeper-client.ts` (base URL из переменной окружения `WORDKEEPER_API_BASE` — только для этого скрипта, в `env.ts` не добавлять), с таймаутами, ретраями и кэшем ответов в `scripts/.cache/wordkeeper/`.
   - Если документации нет или первые запросы возвращают 401/404 — **не гадать эндпоинты в цикле**: сделать максимум 3 осмысленных пробных запроса, затем перейти в офлайн-режим, а в отчёте и в итоговом сообщении явно указать: «API Wordkeeper не подтверждён; онлайн-часть пропущена; действие человека: прислать документацию API или выгрузку частотности в CSV». Ключ никогда не логировать.
