## Technical Details

### Порядок работ

1. **Подготовка окружения:** проверить, что на staging развёрнут образ нужного коммита (`/api/health/` отвечает, версия/SHA в ответе или в деплоях Dokploy); наполнение: сид `--full` + импортированное портфолио (черновики) + привязанные временные изображения; тестовые пользователи `admin`/`manager` (создаёт человек; пароли в менеджере, **не в репозитории**); тестовый почтовый ящик перехвата. Если чего-то нет — остановиться и запросить у человека.
2. **Запуск автоматики** (`scripts/acceptance/run-staging.sh`, параметры `BASE_URL`, `STAGING_BASIC_AUTH`):
   - `pnpm test` (Vitest) и `pnpm lint && pnpm typecheck && pnpm build` на коммите релиза;
   - `e2e/all-urls.spec.ts` против staging (для базовой авторизации — `httpCredentials` в Playwright `use`);
   - `e2e/acceptance/*.spec.ts`;
   - `pnpm audit:content --rendered` против staging;
   - `pnpm audit:seo` — **против локальной production-подобной сборки** (`SITE_ENV=production`, та же БД-снимок/сид), потому что staging по определению noindex и закрыт basic auth (проверки индексации там неприменимы); на staging проверяются заголовки и noindex staging (должны быть **включены**);
   - Lighthouse (mobile) по `scripts/perf/routes.ts` против staging с заголовком `Authorization: Basic …` (`--extra-headers`), медиана из 3 прогонов; сравнение с `docs/reports/performance.md`;
   - `pnpm smoke:prod` с `SMOKE_BASE_URL=<staging>`, `SMOKE_EXPECT_ENV=staging` (инвертированные проверки индексации).
3. **Ручные/полуавтоматические сценарии** (выполняются через Playwright; шаги, не поддающиеся автоматизации, помечаются `[ЧЕЛОВЕК]`).
4. **Security-аудит** (раздел ниже).
5. **Fix list → исправления → повторный прогон** до закрытия всех блокирующих.
6. **Release notes и отчёт.**
7. **Промоут на prod** (только после явного подтверждения человека).

### Сценарии (Playwright, на staging)

1. **Заявка из квиза:** пройти 7 шагов (триплекс 6+6 + плёнка 0,76, 80 м², отверстия, файл DWG-фикстура <1 МБ), согласие, отправка → экран успеха; в админке `/admin/collections/leads/` заявка с корректным JSON ответов, нормализованными колонками, флагами (`nonstandard_size` и т.п.), страницей входа, UTM (прийти по `?utm_source=test&utm_medium=cpc`), файл скачивается из админки и **не** скачивается анониму (`/api/lead-files/<id>/download/` → 401/403); письмо менеджеру появилось в перехватчике (адрес перехвата, тема, таблица данных, ссылка на заявку).
2. **Файл >50 МБ и неверный формат:** отклоняются с текстами из `teksty/05-kviz.md` на клиенте и на сервере (прямой `curl` без UI — 413/415); подмена расширения (`.pdf` с чужим содержимым) отклоняется по сигнатуре.
3. **Антиспам:** honeypot-поле заполнено → 200, но заявка не создана; отправка быстрее 3 с → отклонена; 6 заявок за 10 минут с одного IP → 429 (проверить корректность определения IP за Traefik: заголовок `X-Forwarded-For` с подмененными левыми значениями не обходит лимит).
4. **Дубли:** вторая заявка с тем же телефоном → подсветка дубля в списке.
5. **Заказ:** в админке перевести заявку в статус «Договор» → создан заказ с номером, ссылка `/zakaz/<token>/` открывается без логина; сменить статус на «В производстве» (с комментарием и датой) → письмо клиенту (в перехвате) со ссылкой; «Упаковано» + загрузка 3 фото → галерея с лайтбоксом «1 из 3»; «Отгружено» + ТК/накладная → кнопка «Скопировать» → «Скопировано»; «Получено»; отозвать ссылку → страница «Ссылка больше не действует — свяжитесь с менеджером»; перевыпустить → новая ссылка работает, старая — нет. На странице нет телефона/e-mail заказчика; заголовки `Cache-Control: private, no-store`, `X-Robots-Tag`/meta noindex.
6. **Роли:** `manager` не видит коллекцию `users` (кроме себя), не удаляет заявки, может править `prices` и `promo`, не может править страницы/глобалы остальные; `admin` — полный доступ.

### Security-аудит (OWASP Top 10:2025)

Выполнить с помощью навыка/агента `security-scanner` по репозиторию и живому staging; результат — `docs/reports/security-audit.md` (находка, CWE/OWASP-категория, серьёзность Critical/High/Medium/Low, воспроизведение, исправление, статус). Обязательные направления:

- **A01 Broken Access Control:** Payload REST/GraphQL анонимно: `leads`, `orders`, `lead-files`, `order-files`, `consent-log`, `rate-limits`, `search`, `users` недоступны (ожидается 401/403), публичны только то, что нужно сайту; IDOR: `/api/lead-files/[id]/download/` и `/zakaz/<token>/docs/<id>/` — чужие id/токены; роль `manager` не повышает привилегии (`PATCH /api/users/<id>` с `roles`); `GraphQL` и playground отключены/закрыты в prod; перебор токена заказа (128 бит; есть ли rate-limit на `/zakaz/*` — рекомендовать).
- **A02 Security Misconfiguration:** заголовки (HSTS на prod, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options: SAMEORIGIN`, `Permissions-Policy`; отсутствие CSP — рекомендация с учётом Метрики/карты, report-only), `X-Powered-By` отключён, источники карт отключены в prod (`productionBrowserSourceMaps` выключены), ошибки не раскрывают стек, `/admin` и `/api` не индексируются, `NODE_ENV=production`, нет `.env` в образе, `payload.config` не включает `debug`.
- **A03 Supply chain:** `pnpm audit --prod`, актуальность `next` и `payload` (известные CVE для Next/Payload на момент проверки — проверить через Exa/GitHub advisories), точные версии, отсутствие ненужных пакетов; lock-файл закоммичен; GitHub Actions — версии действий закреплены по SHA/major, `permissions` минимальны.
- **A04 Cryptographic failures:** `PAYLOAD_SECRET`/`FORM_HMAC_SECRET`/`ORDER_TOKEN_SECRET` — из env, не в коде, разные для staging и prod; токен заказа — 128 бит, `HMAC-SHA256(ORDER_TOKEN_SECRET, id + tokenCreatedAt)` (task-18), в БД только SHA-256, перевыпуск меняет токен; сравнение токенов постоянным временем; cookie админки `HttpOnly`, `Secure`, `SameSite` (Lax/Strict).
- **A05 Injection:** сырой SQL в поиске (`src/lib/search/query.ts`) — только параметризованные запросы; `tsquery` собирается из очищенных токенов; XSS: сниппеты поиска (`<mark>` санитизирован), отражённый ввод на `/poisk/`, Lexical-рендер (нет `dangerouslySetInnerHTML` с пользовательским HTML), параметр `src` квиза и открытые редиректы, имена файлов (path traversal, `..`, нулевые байты, длинные Unicode), header injection в письмах (имя/тема из пользовательских данных), CSV/XLSX-инъекции в экспорте (формулы `=`, `+`, `-`, `@` экранировать префиксом `'`).
- **A06 Insecure design:** антиспам (honeypot, HMAC-метка, rate-limit), обход определения IP, лимиты размеров тела (`/api/forms/lead/` JSON-лимит), upload: лимит 50 МБ на сервере (стриминг), signature-проверка, temp-очистка, нет исполнения загруженных файлов, `Content-Disposition: attachment` при скачивании, `X-Content-Type-Options`.
- **A07 Authentication failures:** блокировка после N неудачных входов в админку (`maxLoginAttempts`, `lockTime`), политика паролей, сброс пароля (письмо), создание первого пользователя закрыто после появления админа, сессии/токены отзываются.
- **A08 Data integrity:** подпись формы (HMAC) нельзя подделать; миграции не принимают внешний ввод; образ собран из CI (SHA), а не локально.
- **A09 Logging/monitoring:** ошибки логируются без ПДн и секретов; ключи не в логах; события безопасности (неудачные входы, 429) видны в логах.
- **A10 SSRF/Mishandling of exceptional conditions:** нет серверных запросов по пользовательским URL; необработанные исключения не раскрывают детали; сбой БД/SMTP не роняет форму (письмо через очередь с ретраями; заявка сохраняется независимо от SMTP).
- **ПДн (152-ФЗ):** `consent-log` пишется при каждой заявке (версия политики/согласия, IP, UA); удаление по запросу субъекта работает; бэкапы с ПДн — в приватном бакете РФ; cookie-баннер; аналитика после согласия.

Критичные (Critical/High) находки блокируют релиз: исправить или вернуть координатору. Medium — исправить, если ≤ 30 минут, иначе в fix list с владельцем и сроком. Low — в список рекомендаций.

### Fix list (`docs/reports/fix-list.md`)
